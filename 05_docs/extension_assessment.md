# SRW4S v0.99W 긴 대사 확장 구조 조사

기준: E:/4robot의 원본 Rev 1 및 해시 확인된 v0.99W. 실제 이미지 읽기·압축 해제·MIPS 역어셈블과 공개 빌더를 대조했다. 게임/번역/원본을 수정하지 않았다. 런타임 PoC는 미수행.

## 결론

아크 E2와 같은 '짧은 참조로 다른 위치의 긴 본문을 출력'하는 접근은 가능성이 높다. 그러나 모든 문자열을 하나의 새 opcode로 처리하는 구조가 아니다. MAP의 기존 FB 문자열 호출, 전투의 FC07 상대 점프, D_NAMES 소비자를 각각 구분해야 한다. 0xE2는 이 게임에서 글리프 범위이므로 아크 코드를 그대로 이식할 수 없다.

## 1. MAP: 기존 FB 호출을 먼저 검증

- 실제 0x8011046C 핸들러는 인수 두 바이트를 합쳐 selector를 만든다. 인수 FF는 동적 치환이므로 고정 번호로 쓸 때 피해야 한다.
- selector >= 0x9000이면 bank/slot로 나눠 0x80154080을 호출한다.
- 현재 문자열 커서를 s0에 보존하고, 호출된 문자열을 0x801116E8로 처리한 다음 0x801105CC에서 커서를 복원한다. 이것은 E2와 유사한 호출/복귀의 직접적인 정적 증거다.
- 형태: 기존 표시 본문 자리에 `FB lo hi FF`(독립 문자열 대체 예시)를 두고 대상 슬롯에 긴 본문을 둔다. 기존 이벤트의 종결·대기·선택 제어는 해당 소비자 계약에 맞게 유지해야 한다. 네 바이트조차 확보되지 않는 문자열에는 바로 적용할 수 없다.
- 0x80154080은 CD에서 0x400바이트를 읽고 깊이 인덱스*0x400 버퍼에 복사한다. 0x801116E8은 관련 깊이 변수를 증가시킨다. 중첩 버퍼 수/수명/감소 경로는 추가 확인해야 하며 무제한 중첩은 허용할 수 없다.
- M_BANKS는 현재 742,191B, nonzero 헤더 56개. 정렬한 헤더 사이 간격으로 계산한 최대 물리 블록은 64,305B다. 옛 문서의 39,460B 최대치는 현행 수치가 아니다. 모든 뱅크에 넉넉한 여유가 있다는 가정은 금지한다.
- 먼저 기존 재배치로 늘릴 수 있는 본문을 처리하고, 고정 배치 본문에만 FB 후보를 검토한다. 새 selector는 미사용 증명, STAYDAT 헤더/표 사본 동기화 및 개별 64KiB 오프셋 제한이 필요하다.

## 2. 전투: FC07 점프를 이용한 제자리 우회 후보

- 실제 BATTLE 0x80163F90의 FC 보조표에서 index7은 0x8015A024를 가리킨다.
- 이 함수는 s16을 읽고 `대상 = 인수 주소 + sign_extend(s16)`을 반환한다. `FC 07 <s16>`는 네 바이트, 범위는 -32768..32767이다.
- 중요 정정: index6은 0x8015A01C의 `jr ra; move v0,a0`다. 공개 mbankb_jumpfix.py 주석의 '6·7 둘 다 상대 점프'를 그대로 믿으면 안 된다. 현행 이미지에서 직접 s16을 더하는 함수는 index7이다.
- 후보: 원래 진입 위치와 키/메타데이터를 유지하고 순수 본문 시작에 FC07을 넣어 가까운 확장 본문으로 우회한다. 필요하면 끝에서 원래 후속 명령으로 점프한다. 이는 자동 복귀 호출이 아니므로 종료/후속 실행 위치를 별도로 설계해야 한다.
- 들어오는 참조를 모두 옮기는 방식보다 유리할 수 있지만, 문자열 중간 진입·키 런 순차 탐색·이름표의 위치 의미까지 해결해 주는 것은 아니다. 해당 범위는 별도로 소비자 검증해야 한다.
- 실제 M_BANKB 해제 크기: 원본 55,353B -> v0.99W 59,210B. 이미 3,857B 확장돼 있다.
- 빌더 기본 MAX_BLOB 61,320B와 차이는 2,110B다. 이는 조건부 상한까지의 산술 차이이며 런타임 보장된 추가 용량이 아니다. 압축본은 기존 17섹터 예산도 만족해야 한다.
- 기존 BATTLE 뒤 공간은 애니메이션 데이터였고 스프라이트 소실 회귀 때문에 사용 중단된 코드가 있다. 현행 BATTLE.LZB가 원본과 동일한 사실과 부합한다. 그 공간을 무료 확장 RAM으로 재사용하지 않는다.
- 0x8015A7B8은 selector bit15에 따라 0x80146EEC/0x80146EC0 소비자를 고른다. 새 본문이 한 사본에만 있으면 다른 경로에서는 실패할 수 있다. C_BEFCT도 따로 조사해야 한다.

## 3. D_NAMES/UI/이름

STAYDAT의 D_NAMES 슬롯은 빌더상 55,296B다. 별도 D_NAMES 파일을 늘리는 것만으로 상주 사본이 바뀌지 않는다. MAP FB 경로가 D_NAMES도 참조하지만, 모든 UI/이름 소비자가 FB를 해석한다는 증거는 아니다. 고정 길이 이름 복사기는 긴 본문 저장과 별개로 복사 길이·종결자·출력 폭을 제한한다. 이런 이름에는 접근자/복사기별 수정이 필요할 수 있다.

## 권장 PoC 순서

1. MAP에서 현재 문장과 바이트 동일한 별도 본문을 만들고 FB로 호출: 출력·복귀·다음 이벤트·대기/선택 제어 확인.
2. 검증된 대상 하나만 길게 변경: 1KB 창, 줄/페이지, 버퍼 수명 확인.
3. 전투의 단순 구호 하나를 동일 본문 FC07 우회: 원래 진입점 유지, s16 도달성, 공격/피격/회피와 사본 확인.
4. 키 런/화자 이름 등 복합 항목은 이후 별도 검증. 미검증 공간 확보나 신규 opcode 개발은 앞 단계 실패 이유가 확정된 뒤 판단.

원장이 없는 상태에서도 바이너리 동일 본문의 우회 PoC 설계는 가능하다. 정식 번역 편집·전체 재빌드에는 번역 원장과 문자 할당표 복원이 필요하다.
