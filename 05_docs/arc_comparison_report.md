# 아크더래드 1의 실패 사례로 해석하는 슈로대 S 글꼴 시험

작성일: 2026-09-13. 근거는 로컬 Arc 1 작업 기록과 슈로대 실행 시험 결과이다. 이번 문서는 신규 실행 시험을 추가한 결과가 아니라 기존 증거의 비교 분석이다.

**현재 판단: 완성형 글꼴을 유지하며 RAM에서 필요한 글리프를 교체하는 방향으로 진행할 근거가 생겼다. 그러나 동적 캐시 완성이나 전 구간 VRAM 안전성을 입증한 단계는 아니다.**

## 1. 아크에서는 무엇이 실패했나

아크의 과거 동적 캐시는 완성형 글자를 VRAM의 작은 영역에 올리고, 그 위치를 화면 그리기 명령이 참조하는 방식이었다. 문제는 그 영역을 게임도 사용했다는 것이다.

- v210 기록: 캐시의 물리 VRAM 범위 x=961..981, y=480..491이 세계지도 그림의 원천 영역과 전부 겹쳤다. 글꼴을 올리면 지도에 글꼴 픽셀이 섞일 수 있었다.
- 이후 기록: 게임이 그 위치에 그림을 올리면 반대로 캐시 글자가 사라졌다. 캐시 관리표에는 글자가 있다고 남아 있어도 실제 VRAM 픽셀은 이미 다른 내용이었다.
- 매 프레임 재업로드도 만능 해결책이 아니었다. 같은 자리를 서로 덮으면 지도와 글자 사이의 충돌은 계속된다.
- 조사 상태를 늘리자 빈 공간으로 보였던 후보들이 사용 중으로 드러났다. 픽셀이 0인 영역도 게임이 0을 쓰는 영역일 수 있어, 검은 화면만 보고 빈자리라고 판정할 수 없었다.
- 좌표를 옮길 때 업로드 목적지와 화면 명령의 U/V 좌표가 함께 맞아야 했다. 이 좌표 경로 문제도 별도로 있었다. 모든 실패가 단순 용량 부족은 아니었다.

따라서 당시 실패를 “PS1에서는 완성형 캐시가 불가능하다”로 일반화하면 안 된다. 정확한 교훈은 **게임이 소유한 VRAM에 별도 글리프 저장소를 얹으면 충돌하고, 그 저장소를 참조하는 경로까지 함께 관리해야 한다**는 것이다.

## 2. 이번 슈로대 시험은 무엇을 바꿨나

원본 디스크나 기존 패치 이미지는 수정하지 않았다. 별도 PS1 에뮬레이터 프로세스에서 같은 상태와 같은 입력을 사용해 두 실행을 비교했다.

1. 기준 실행: RAM 폰트를 그대로 둔다.
2. 진단 실행: RAM 주소 0x80057838부터 49,152바이트의 전각 폰트만 0으로 만든다.
3. 이미 표시된 문구를 유지한 상태와, 다음 문구를 표시한 상태를 각각 비교한다.
4. 화면 이미지뿐 아니라 저장 상태에서 추출한 VRAM 전체 1MiB를 비교한다.
5. 메뉴에서는 폰트를 복원하고 다시 그렸을 때 기준으로 돌아오는지도 확인했다.

폰트를 0으로 만든 것은 최종 패치가 아니다. “게임이 이 폰트를 언제 읽는가”를 확인하려고 글자 모양을 의도적으로 없앤 진단이다. 새로운 완성형 글꼴의 미관이나 올바른 문자 매핑을 시험한 것도 아니다.

“차이 0”은 같은 순간의 기준 실행과 진단 실행이 같다는 뜻이다. 게임의 VRAM이 그 시간 동안 아무 변화도 없었다는 뜻은 아니다. 또한 900프레임의 두 화면 일치는 검은 장면 전환에서 나온 결과여서 글꼴 안전성의 주된 근거로 사용하지 않는다.

## 4. 왜 아크보다 유리한 단서인가

비유하면 RAM 글꼴은 도장, 이미 출력된 문구는 찍힌 종이다. 이번에는 도장의 글자 모양을 지워도 이미 찍힌 종이는 그대로였고, 새로 찍을 때만 글자가 사라졌다.

아크의 문제 경로에서는 화면이 참조하는 VRAM 도장 보관함을 지도 그림과 공유했다. 슈로대의 관측 결과는 RAM의 도장을 기존 텍스트 출력 경로로 찍어 두는 방식과 부합한다. 따라서 RAM 쪽 글리프 공급을 바꾸고 게임의 기존 출력 공간을 유지하는 설계를 우선 검토할 수 있다.

다만 이번 시험에서 아크와 같은 VRAM 충돌을 재현하지 않았다는 사실만으로 충돌 가능성이 0이 되지는 않는다. 애초에 새 VRAM 캐시를 만들지 않은 시험이기 때문이다. 입증한 것은 기존 출력과 RAM 폰트 원천이 관측 경로에서 분리된다는 점이다.

| 항목 | 아크의 과거 동적 캐시 | 슈로대의 현재 검토 방향 |
|---|---|---|
| 교체하려는 위치 | 별도 VRAM 글리프 영역 | 기존 RAM 글꼴 영역 또는 검증된 RAM 작업 공간 |
| 그래픽 충돌 핵심 | 게임 그림과 글리프가 같은 VRAM 사용 | 추가 VRAM 영역을 요구하지 않는 설계 우선 |
| 기존 글자와 교체 관계 | 참조 중인 VRAM 슬롯 관리가 중요 | 시험에서는 기존 출력이 RAM 폰트 삭제 후에도 유지 |
| 아직 해결할 문제 | 점유·좌표·슬롯 수·재업로드 | 글리프 ID·교체 시점·RAM 수명·모든 출력 경로 |

## 5. 완성형 1비트 글꼴과 맵별 로딩은 가능한가

16×16 1bpp는 한 글자 32바이트다. 현 전각 폰트 1,536칸은 48KiB이며, 현대 한글 11,172자를 모두 저장하면 357,504바이트, 약 349KiB다. 이는 비트맵 원천의 저장량 계산이지 VRAM 추가 사용량이 아니다. 표·정렬·기타 문자 공간도 별도다. 1비트 원천이 그대로 1비트 VRAM 텍스처가 된다는 뜻도 아니다.

전체 한글을 디스크에 두고 필요한 부분만 RAM에 넣는 방안은 검토 가치가 있다. 다만 “맵에 필요한 글자만 넣으면 된다”에는 조건이 붙는다. 해당 맵의 대사 외에도 메뉴, 아이템·기체·화자 이름, 전투 구호, 사용자 입력 이름 등에서 요청되는 글자를 포함해야 한다. 게임이 현재 이미 맵별 한글 로딩을 한다고 확인한 것은 아니다.

우선순위는 다음과 같다.

1. 실제 완성형 글꼴 A/B 두 묶음 교체 시험: 기존 표시 유지, 새 문구 정확성, 폰트 복귀를 확인한다.
2. 공통 문자와 장면별 문자의 집합을 계산한다. 최대 글리프 수를 실측하고 고정 슬롯에 들어가는지 확인한다.
3. 충분하면 공통 글자 고정 + 장면별 선로딩부터 구현한다. 전환 순간의 RAM/오버레이 수명도 검사한다.
4. 집합이 넘치거나 요청을 예측하기 어려우면 문구/페이지 단위 선로딩 또는 RAM 동적 캐시로 세분화한다. 렌더링 도중 CD에서 한 글자씩 읽는 설계는 성능 검증 없이 채택하지 않는다.

기본 저장 단위가 16×16인 것은 완성형 비트맵을 넣기 좋은 조건이다. 하지만 실제 글자의 선명도·여백·폭·줄간격은 새 폰트로 화면을 보고 판단해야 한다. 기존 도구의 16×16 틀이 곧 최종 글자 외형 16×16을 뜻하지는 않는다.

## 6. 축약 없는 재번역까지 남은 거리

글리프 제한을 풀면 “이 한글이 없어서 다른 단어를 쓰는 문제”를 해결할 수 있다. 그러나 “문장이 바이트 칸에 안 들어가서 줄이는 문제”는 별도다.

상대 점프, 문장 중간 진입, 이름 복사 길이, 대사 사본, 화면 줄·페이지 처리도 풀어야 한다. 그러므로 이번 결과만으로 모든 대사를 길이 제한 없이 재삽입할 수 있다고 말할 수는 없다. 번역문의 의미를 보존하기 위해 폰트 공급과 장문 처리를 두 작업으로 진행해야 한다.

## 7. 판정과 한계

- 판정: 완성형을 포기하고 조합형으로 갈 이유는 아직 없다. 추가 VRAM 글리프 영역을 만들지 않는 RAM 공급 방식부터 시험할 근거가 충분하다.
- 미완료: 실제 새 완성형 폰트 교체, 캐시 알고리즘, 새 RAM 영역 확보, 로딩 성능, 장면 전환 전체, 전수 플레이.
- 환경 한계: mednafen 소프트웨어 PS1 코어로 실행했으나 보유 BIOS 해시가 코어 권장값과 달랐다. 지원 BIOS 및 독립 에뮬레이터 재시험이 필요하다. 실기 하드웨어 검증은 아니다.
- 표본 한계: 일부 UI·맵·첫 전투이다. 가라오케·모든 컷인·모든 메뉴까지 안전하다고 확장 해석하지 않는다.
